# Frontend map (Angular 21)

Standalone components, no NgModules. State lives in root services as private signals exposed read-only and derived with `computed()`; every mutation writes the whole object back through `StorageService`, which now calls the FastAPI backend (see [backend.md](backend.md)) instead of `localStorage`, scoped per logged-in account. The recipe catalog also loads from the backend, asynchronously, so it starts empty and populates once the HTTP call resolves - see G11. That catalog is discovery-only (root recipes, public + your own); a private recipe you already reference (favorited/planned) or a twist resolves through a by-id fallback - also G11. Browsing (home, recipe catalog, recipe detail, cooking mode) needs no account; only account-linked features (favorites, ratings, notes, meal plan, collections, shopping list, editing/twisting/visibility on recipes) require login (`AuthService`, `authGuard`) - see G13 and the auth flow below. Accounts use a username, not an email. Styling is Tailwind with class-based dark mode, plus per-component SCSS.

## Core flow: schedule to shopping list

1. On the meal plan page, `src/app/pages/meal-plan/meal-plan.component.ts` `addMeal()` passes date, recipe id, meal type, and servings to the service.
2. `src/app/services/meal-plan.service.ts` `addMeal()` stores a `PlannedMeal` inside the matching day of the single `WeeklyPlan`.
3. The page's generate button calls `generateShoppingList()` in `src/app/pages/meal-plan/meal-plan.component.ts`, which calls `generateFromMealPlan()` and navigates to /shopping-list.
4. `src/app/services/shopping-list.service.ts` `generateFromMealPlan()` sums servings per recipe across the whole plan, then `generateFromRecipes()` scales each recipe by planned servings / `recipe.servings`, merges items with the same lowercase name + category (quantities summed, rounded to 2 dp, sources kept in `recipeIds`), and replaces the current list.
5. `src/app/pages/shopping-list/shopping-list.component.ts` shows the list grouped by category via `getGroupedItems()`, with a `completionPercentage` bar.

Pages link to each other with the `addRecipe` query param: on /meal-plan it preselects the recipe in the form; on /shopping-list it rebuilds the list from that one recipe (see G2).

## Core flow: auth

1. `src/app/services/auth-state.ts` holds the session as plain (non-DI) module state - `userSignal`, `initializedSignal`, `isAuthenticated`, plus `getToken()`/`setToken()`/`clearToken()` over a `localStorage` token key - specifically so it can be read from both `AuthService` and the HTTP interceptor without Angular DI ever resolving `AuthService` from inside the interceptor (see G12).
2. `src/app/services/auth.service.ts` wraps that state for components: on construction it calls `getToken()` and, if present, `GET /api/auth/me` to populate `userSignal`; `initializedSignal` flips true once that check resolves either way. Exposes `currentUser`, `isAuthenticated`, `initialized`, `register()`, `login()`, `logout()`.
3. `src/app/guards/auth.guard.ts` `authGuard` blocks every real page until `initialized` is true, then redirects to `/login` if `isAuthenticated()` is false; `guestGuard` does the reverse for `/login` and `/register`.
4. `LoginComponent`/`RegisterComponent` (`src/app/pages/login`, `src/app/pages/register`) call `AuthService.login()`/`register()`, which store the returned token and user, then navigate to `/`.
5. `src/app/interceptors/auth.interceptor.ts` attaches `Authorization: Bearer <token>` to every request to the API base, reading straight from `src/app/services/auth-state.ts`. It only forces a logout+redirect on a 401 when a token was actually sent (a rejected/expired session); a 401 with no token is the expected shape of a guest hitting an account-only endpoint and is left for the caller to degrade gracefully (see G13).
6. `src/app/app.ts`/`src/app/app.html` always render `NavbarComponent`; it shows "Sign in"/"Sign up" links when logged out and the user's name + "Log out" when logged in.
7. Only `src/app/app.routes.ts` routes for `add-recipe`, `meal-plan`, `favorites`, `collections`, and `shopping-list` carry `canActivate: [authGuard]`. Account-linked actions reachable from public pages (favorite/rate/notes on `src/app/pages/recipe-detail/recipe-detail.component.ts`, `toggleFavorite()`/`setRating()` in `src/app/services/recipe.service.ts`) check `isAuthenticated()` from `src/app/services/auth-state.ts` themselves and redirect to `/login` if logged out, since the route itself isn't guarded.

## Core flow: adding or editing a recipe

1. `src/app/components/recipe-form/recipe-form.component.ts` (`RecipeFormComponent`) owns the whole form: basics, dynamic ingredients/steps (steps are optional - can be emptied to 0, see the cooking-mode gotcha below), dietary restrictions (quick-pick chips from `SUGGESTED_DIETARY_RESTRICTIONS` in `src/app/models/recipe.model.ts` plus a free-text `addCustomDietary()` for any value not listed), nutrition, tags/tips, and the camera/file photo capture. It takes an optional `initialRecipe` input (prefills every field, including treating the existing image as already uploaded) and emits `save` with the assembled `RecipeCreateInput` - it never calls the backend itself.
2. `src/app/pages/add-recipe/add-recipe.component.ts` renders the form with no initialRecipe and calls `RecipeService.createRecipe()` on save; the id, rating, review count, author, date-added, owner, visibility, official flag, and twist lineage are all assigned server-side (see backend.md). A new recipe is public by default.
3. `src/app/pages/edit-recipe/edit-recipe.component.ts` (route /recipes/:id/edit, authGuard) resolves the recipe via `RecipeService.resolveRecipe()` the G11-safe way, redirects away if the current user isn't its ownerId, renders the form with initialRecipe set, and calls `RecipeService.updateRecipe()` on save.
4. The photo input (`<input type="file" accept="image/*" capture="environment">`) opens the device camera on mobile, or a file picker on desktop. `onImageSelected()` previews the file locally (`URL.createObjectURL`) and immediately calls `StorageService.uploadImage()`, which posts multipart form data to `POST /api/images`; the backend uploads it to Cloudinary and stores it as AVIF regardless of the source format, returning the CDN URL.
5. Submitting is disabled (`canSubmit`) until any in-progress upload finishes and every required field is filled - a photo is optional (submits with `image: ''`, falls back to `ImagePlaceholderComponent` same as a broken image URL) and so are steps (can be emptied to 0). `removeImage()` clears a chosen photo (and resets the file input so the same file can be re-picked) without requiring a re-upload to change your mind.
6. On success, both pages append/replace the server's response in `recipesSignal` (via `RecipeService`'s internal `mergeRecipe()`) - no full refetch needed - then navigate to `/recipes/:id`.

## Core flow: twists (forking someone else's recipe)

1. On `src/app/pages/recipe-detail/recipe-detail.component.ts`, `canTwist()` shows "Add to my book" when the viewer is logged in, isn't the recipe's owner, and the recipe isn't itself already a twist (`parentRecipeId` is null) - twisting a twist isn't offered in the UI, though the backend doesn't hard-block it.
2. `addToMyBook()` calls `RecipeService.twistRecipe()` -> `POST /api/recipes/{id}/twist`, which creates a full copy owned by the caller, private by default, linked back via `parentRecipeId`, then navigates to the new twist's own detail page.
3. Twists never appear in discovery (`RecipeService.recipes()` or its filtered view), even the owner's own and even once published - `GET /api/recipes` only ever returns root recipes. They're reachable via the original's "Twists of this recipe" section (RecipeService.getTwists, documented on recipe.service.ts above) or the owner's `src/app/pages/my-recipes/my-recipes.component.ts` page.
4. A twist can be made public the same way any recipe's visibility is toggled (see below); publishing it still doesn't add it to discovery.

## Core flow: recipe visibility ("unlisted", not deleted)

1. `RecipeService.updateRecipe(id, { isPublic })` (called from `recipe-detail.component.ts` `toggleVisibility()` and `my-recipes.component.ts` `toggleVisibility()`) is the only way a recipe's visibility changes; only the owner can call it (enforced server-side).
2. Going private only removes a recipe from the discovery-backed `recipesSignal` (via `GET /api/recipes`, which filters to public + your own root recipes) - it does not delete anything or block direct-by-id access. Anyone who already favorited it, planned it, or linked to it as a twist's parent keeps working, because `GET /api/recipes/{id}` never checks visibility.
3. See gotcha G11 below for how pages that need a specific recipe by id, rather than the discovery list, fall back to that direct fetch.

### Services (barrel `src/app/services/index.ts`)
Every service: private signal, public read-only view, loads from storage in the constructor, saves the whole object after each mutation.
- `src/app/services/storage.service.ts` - HTTP wrapper over the FastAPI backend's `/api/storage/{key}` and `/api/recipes` endpoints, see backend.md; methods return Observables, same shape as the old localStorage-based version. Keys: favorites, ratings, collections, mealPlan (now an array of weekly plans, see the meal-plan service below), shoppingList, per-recipe notes, recentViews, darkMode (still frontend-only in practice, but round-trips through the backend like everything else). `getRecipes()` fetches the discovery catalog; `createRecipe()` posts a new one (no `catchError` - callers need the real error to show feedback); `updateRecipe()` PATCHes edits/visibility; `deleteRecipe()` DELETEs (owner-only, enforced server-side); `getRecipeById()` fetches one recipe regardless of visibility, swallowing a 404 to `null` (used for the "unlisted" fallback); `getMyRecipes()`, `twistRecipe()`, `getTwists()`, `setRecipeOfficial()` back the twist/official/My-Recipes features; `uploadImage()` posts multipart form data to `POST /api/images` and resolves the Cloudinary URL.
- `src/app/services/recipe.service.ts` - catalog loaded async from `StorageService.getRecipes()` into `recipesSignal` (starts empty, see G11; holds discovery-visible root recipes only), plus favorites, ratings, filter/sort/view state. Key names: `filteredRecipes` (also filters by `originFilter` for Official/Community), `favoriteRecipes`, `recipesLoaded`, `scaleRecipe()`, `toggleFavorite()`, `setRating()`, `updateFilter()`, `getRecipeById()` (sync, reads `recipesSignal` only), `getRecipesByIds()`, `getQuickRecipes()` (30 min or less total), `createRecipe()`, `updateRecipe()`, `resolveRecipe()` (async fallback: fetches by id and merges into `recipesSignal` if not already loaded - see G11), `twistRecipe()`, `getTwists()`, `loadMyRecipes()`, `setOfficial()`, `deleteRecipe()` (removes from `recipesSignal` on success), `recordView()` (auth-gated, dedupes/caps at 10, persisted via `StorageService.setRecentViews()`), `recentlyViewedRecipes` (computed, most-recent-first). `toggleFavorite()`/`setRating()` redirect to `/login` if logged out instead of silently failing to persist (see G13).
- `src/app/services/collection.service.ts` - `Collection` CRUD: `createCollection()`, `addRecipeToCollection()`, `getRecipesInCollection()`, `getCollectionsForRecipe()`.
- `src/app/services/meal-plan.service.ts` - keeps a full history of `WeeklyPlan`s (one per week ever visited, not just one active plan - planning ahead or looking back never erases another week), stored as an array under the same `mealPlan` storage key (old single-object-shaped data from before this existed is migrated into a one-item array on load). `mealPlan` is a `computed()` pointing at whichever week `goToWeek()`/`goToNextWeek()`/`goToPreviousWeek()`/`goToCurrentWeek()` last selected, auto-creating an empty persisted plan the first time a given week is visited. `addMeal()`, `removeMeal()`, `updateMeal()`, `clearDay()`, `getAllPlannedRecipes()`, `getWeekDates()`, `isRecipePlanned()` all act on the currently-selected week only. `clearMealPlan()` wipes the *entire* history (no UI calls it - it's a full reset, not "move to a new week"). `plansLoaded` mirrors the `recipesLoaded` pattern `src/app/services/recipe.service.ts` uses (see G11) for the async initial load.
- `src/app/services/shopping-list.service.ts` - the single active `ShoppingList`: `generateFromMealPlan()`, `generateFromRecipes()` (both fully replace the list - intentional, see gotcha G2), `addRecipeToList()` (merges one recipe into the existing list instead of replacing it), `addItem()`, `toggleItemChecked()`, `clearCheckedItems()`, `getGroupedItems()`, `getCompletionPercentage()`.
- `src/app/services/toast.service.ts` - in-app replacement for `alert()`: signal `toasts`, `show(message, type?, durationMs?)` auto-dismisses, `dismiss(id)` removes early. Rendered globally by `src/app/components/toast/toast.component.ts` (see below), so any service/component can just inject and call `show()`.
- `src/app/services/theme.service.ts` - `darkMode` signal; an `effect()` persists it and toggles the `dark` class; also follows OS theme changes.
- `src/app/services/auth.service.ts` - `currentUser`, `isAuthenticated`, `initialized`, `isAdmin` signals (delegating to `src/app/services/auth-state.ts`); `register()`, `login()`, `logout()`; validates the stored token against `GET /api/auth/me` on startup.
- `src/app/services/auth-state.ts` - plain, non-injectable module: `userSignal`, `initializedSignal`, `isAuthenticated`, `getToken()`/`setToken()`/`clearToken()` over `localStorage` (bypassing StorageService, see the auth flow above and G12). Imported directly by both `src/app/services/auth.service.ts` and `src/app/interceptors/auth.interceptor.ts`.

## Gotchas (verified 2026-09-27)

- G2 (partially fixed) - `src/app/pages/shopping-list/shopping-list.component.ts` handling the `addRecipe` query param now calls `src/app/services/shopping-list.service.ts` `addRecipeToList()`, which merges one recipe's ingredients into the existing list instead of replacing it. `generateFromMealPlan()`/`generateFromRecipes()` still fully replace the list - that's intentional there, since the "Generate Shopping List" button on the meal-plan page is an explicit "rebuild from my whole plan" action, not an additive one.
- G4 - The dietary filter is OR, not AND. `src/app/services/recipe.service.ts` `filteredRecipes` keeps a recipe matching any selected restriction, so Vegan + Gluten-Free also shows recipes that are only Vegan.
- G5 - Date math mixes UTC and local time. `src/app/pages/meal-plan/meal-plan.component.ts` and `src/app/services/meal-plan.service.ts` build date strings with `toISOString()` (UTC), so "today" and the plan's Monday can shift a day near midnight. `addDays()` parses as UTC but adds with `setDate()` (local), so a plan longer than 7 days that crosses a daylight-saving change repeats one date and drops the last day. Switch to UTC date math (setUTCDate) before supporting longer ranges.
- G8 - Shopping items merge without checking units. `src/app/services/shopping-list.service.ts` `generateFromRecipes()` keys on name + category only, so "2 tbsp butter" + "1 cup butter" becomes "3 tbsp". The seed data has 32 shared ingredients whose units differ between recipes.
- G9 - `src/app/services/recipe.service.ts` `scaleRecipe()` also multiplies `nutrition`, but seed nutrition is per serving (the detail page labels it that way and correctly shows the unscaled values). Don't display scaled nutrition as per-serving.
- G10 - `src/app/services/meal-plan.service.ts` `getAllPlannedRecipes()` returns each recipe once even when planned several times, because `getRecipesByIds()` in `src/app/services/recipe.service.ts` filters the catalog. `generateFromMealPlan()` in `src/app/services/shopping-list.service.ts` relies on that: servings are summed first, so a recipe returned twice would be counted double.
- G6 - IDs are generated in the browser (`generateId()` = prefix + timestamp + random) in `src/app/services/meal-plan.service.ts` and the other domain services (meal plan, collections, shopping list). Recipes are the one exception: `POST /api/recipes` now assigns the id server-side (see backend.md) - follow that pattern rather than `generateId()` if any of these other domains gets a real backend table.
- G7 - Stubs and dead code: `toggleIngredientChecked()` in `src/app/pages/recipe-detail/recipe-detail.component.ts` only logs; `UserRecipeData` in `src/app/models/collection.model.ts` is unused. `getRecentViews()`/`setRecentViews()` in `src/app/services/storage.service.ts` are no longer dead - see `RecipeService.recordView()` above.
- G11 - The recipe catalog is no longer available synchronously, and it's also no longer the complete set of recipes a page might need. `src/app/services/recipe.service.ts` fetches it from the backend in the constructor, so `recipesSignal` starts as `[]` and `getRecipeById()` can return nothing for a beat after app start - and even once loaded, it only ever holds discovery-visible root recipes (public + your own, never twists, never someone else's now-private recipe). Any code that reads `RecipeService.getRecipeById()`/`getRecipesByIds()` once (e.g. in `ngOnInit`) instead of reactively off `recipes()` can race a direct page load or refresh; `src/app/pages/recipe-detail/recipe-detail.component.ts` and `src/app/pages/cooking-mode/cooking-mode.component.ts` handle this with an `effect()` keyed on `recipesLoaded()`, and additionally fall back to `RecipeService.resolveRecipe()` (which fetches by id via `StorageService.getRecipeById()` - open regardless of visibility - and merges the result into `recipesSignal`) before concluding a recipe truly doesn't exist. Follow that same two-step pattern (catalog lookup, then `resolveRecipe()` fallback) for any new page that resolves a recipe from a route param or an id saved elsewhere (favorites, meal plan, shopping list, collections, a twist's parent) - a plain "not in `recipes()`" check alone will incorrectly treat a private/unlisted recipe or a twist as missing.
- G12 - Never `inject(AuthService)` inside `src/app/interceptors/auth.interceptor.ts`. `AuthService`'s constructor makes its own HTTP call (`GET /api/auth/me`), which passes back through this same interceptor while the service is still being constructed; injecting `AuthService` there throws `NG0200: Circular dependency detected` (silently swallowed by the request's error handler, so it manifests as every fresh page load bouncing straight back to `/login` a couple seconds after rendering, not as a visible crash). Read/write session state through the plain functions and signals in `src/app/services/auth-state.ts` instead - they carry no DI relationship to `AuthService`.
- G13 - Browsing is public but the backend's `/api/storage/*` endpoints always require a token, so any component that reads account-linked state (favorites, ratings, notes) on a public page - `src/app/services/recipe.service.ts` `loadUserData()`, `src/app/pages/recipe-detail/recipe-detail.component.ts` `loadNotes()` - will get a 401 for a guest. That's expected and handled: `src/app/services/storage.service.ts` `get()` already catches errors and resolves `null`, and `src/app/interceptors/auth.interceptor.ts` only force-redirects to `/login` when a token was actually sent (see the auth flow above), so a guest's failed read just renders as empty state, not a redirect. Any new account-linked read on a public page should rely on that same graceful-null behavior rather than assuming the caller is authenticated; any new account-linked *write* reachable from a public page should check `isAuthenticated()` first the way `toggleFavorite()`/`setRating()`/`saveNotes()` do, since a write's `catchError` only swallows the error - it doesn't warn the user their action didn't save.
- G14 - `src/app/components/recipe-form/recipe-form.component.ts` has no server-side rule stopping the same photo from being uploaded twice: every `onImageSelected()` call hits `POST /api/images` again, even if the user picks a photo, then picks a different one - the first upload isn't deleted from Cloudinary, it's just orphaned (never referenced by any recipe). Fine for a personal project's storage quota today; worth a cleanup job or a "delete previous upload" call if this becomes noticeable.
- G15 - The seed catalog is only 2 recipes (both Italian, both `Category: 'Dinner'`/`'Lunch'`), replacing the earlier 18-dish Algerian catalog. Every other `Category` (`'Breakfast'`, `'Snacks'`, `'Dessert'`), `Difficulty` (`'Easy'`, `'Hard'`), and most `CuisineType` values in `src/app/models/recipe.model.ts` currently have zero matching recipes, so filter chips or category tiles for those will correctly show empty results, not a bug - don't "fix" an empty filtered list without checking the seed data first.
- G16 - `computed()` only re-runs when a *signal* it read changes; a plain field reassigned outside any signal write (like `recipe` on `src/app/pages/recipe-detail/recipe-detail.component.ts`, set imperatively in `setRecipe()`) won't trigger a re-evaluation, so a `computed()` that reads it can cache a stale (often pre-load) value forever - the same class of bug as G1. `isOwner()`/`canTwist()` on that page are deliberately plain methods, not `computed()`, so Angular re-evaluates them fresh on every template check. Don't wrap a derived value in `computed()` if any of its inputs is a plain field rather than a signal.
