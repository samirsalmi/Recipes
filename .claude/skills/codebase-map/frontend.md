# Frontend map (Angular 21)

Standalone components, lazy routes, signals. State lives in root services (private signals,
`computed()` views, `.asReadonly()` exposure); **every HTTP call goes through
`src/app/services/storage.service.ts`** and returns an Observable. The household (plan,
groceries, activity) is shared between members and kept live by activity polling. Phase 2 of
the rework (docs/rework-plan.md) is done: models, services, design system, app shell and route
table and every screen are built (phase 3). Visual QA: `npm run qa:shots` (`scripts/qa-shots.mjs`).

## Core flows

### Plan -> groceries (shared, live)
1. `src/app/pages/recipe-detail/recipe-detail.component.ts` `addToPlan()` (or the Plan page) calls `MealPlanService.addEntry()` in `src/app/services/meal-plan.service.ts`, which posts through `StorageService.addPlanEntry()`; servings default to the household size server-side.
2. The backend logs a plan.add activity row. Other members' `HouseholdService.pollNow()` (in `src/app/services/household.service.ts`) picks it up within ~8 s, toasts "Amina added ...", and emits it on `remoteEvents$`.
3. MealPlanService and `GroceriesService` (`src/app/services/groceries.service.ts`) subscribe to `remoteEvents$` and reload. The grocery list is recomputed server-side from the plan for the open trip; `GroceriesService.aisleGroups` groups it by aisle (fixed `AISLES` order from `src/app/models/recipe.model.ts`), `staples`, `noLongerNeeded`, `optionalExtras` are separate.
4. Checking an item calls `GroceriesService.toggle()` -> `mark()`/`unmark()`; the response is the whole recomputed list, which replaces the signal. If the plan grows after purchase, the item comes back as to-buy with `moreNeeded` and a `remainingLabel`.

### Auth
1. `src/app/services/auth-state.ts` holds `userSignal`/`initializedSignal`/`isAuthenticated` and the token as plain module state, so `src/app/interceptors/auth.interceptor.ts` can read it without DI (G12).
2. `src/app/services/auth.service.ts` validates the stored token via `/auth/me` on startup (which also re-creates a missing household server-side).
3. `src/app/guards/auth.guard.ts` `authGuard` waits for `initialized`, then redirects guests to /login with `returnUrl`; `src/app/pages/login/login.component.ts` and `src/app/pages/register/register.component.ts` follow it (register defaults to /onboarding).
4. Services that hold account data (`FavoritesService`, `HouseholdService`, `MealPlanService`, `GroceriesService`, recent views in `RecipeService`) load/clear from an `effect()` on `isAuthenticated()`.

### Recipe from a route param (G11-safe)
`src/app/pages/recipe-detail/recipe-detail.component.ts` and `src/app/pages/cook/cook.component.ts` read the `id` input, look it up in `RecipeService.recipes()` inside an `effect()` keyed on `recipesLoaded()`, and fall back to `RecipeService.resolveRecipe()` (by-id fetch, merged into the catalog) before showing "not found".

## Gotchas

- G11 - The catalog loads async and only holds discovery recipes (public + your own roots). Resolve a recipe from a route param reactively off `recipes()`/`recipesLoaded()` and fall back to `RecipeService.resolveRecipe()` in `src/app/services/recipe.service.ts` before treating it as missing; plan entries embed a `recipe` summary so the plan never needs a lookup.
- G12 - Never `inject(AuthService)` in `src/app/interceptors/auth.interceptor.ts` (circular DI via the `/auth/me` call); use `src/app/services/auth-state.ts`.
- G13 - Public pages call account endpoints as guests: reads in `src/app/services/storage.service.ts` resolve null/[] on error, and writes reachable from public pages must call `requireLogin()` from `src/app/services/auth-redirect.ts` first.
- G16 - `computed()` only tracks signals; keep page state that derived values read in signals (the detail page's `recipe`/`servings` are signals for that reason).
- G17 - `src/app/services/collection.service.ts` still generates ids in the browser and stores collections as one app_storage blob; fine for per-user data, revisit if collections become shared.
- G18 - Activity polling in `src/app/services/household.service.ts` treats the first page after login/join as history (no toasts); events from the current user are never toasted or re-emitted, since the page already applied the server response.
