# Backend map (FastAPI)

Multi-user API with JWT auth (see [database.md](database.md) for the schema): a recipe
catalog with per-recipe ownership/visibility/curation/lineage, image uploads proxied to
Cloudinary, and a generic key/value store scoped per account that mirrors the app's old
localStorage keys 1:1, so `src/app/services/storage.service.ts` is the only thing that talks
to it. Schema changes go through Alembic (`backend/migrations/`), not create_all. See
`backend/README.md` for setup/run/migration steps.

## Start here by task

| Task | Go to |
|---|---|
| Add or change a recipe field | `backend/app/models.py` `RecipeRow.data` (JSON blob of the whole `Recipe` object) for content fields, or add a real column if discovery needs to filter/sort on it in SQL like `is_public`/`is_official` do - regenerate `backend/app/seed_data.json` from `src/app/data/mock-recipes.ts` and re-run `python -m app.seed` |
| Change the DB schema | Edit `backend/app/models.py`, then `alembic revision --autogenerate -m "..."` and `alembic upgrade head` (see `backend/README.md`) - never rely on create_all |
| Add a new piece of app state (new storage key) | Nothing to add here - `backend/app/routers/storage.py` is generic; just call a new key from `src/app/services/storage.service.ts` |
| Change auth rules, token lifetime, or add an OAuth provider | `backend/app/security.py` (`hash_password()`, `create_access_token()`, `get_current_user()`, `get_current_user_optional()`, `require_admin()`), `backend/app/routers/auth.py` (register/login/me) |
| Change CORS or DB connection | `backend/app/config.py` `Settings` (`database_url`, `cors_origins`, `secret_key`, `access_token_expire_minutes`), read from a local .env file (see `backend/.env.example`); also driven into `backend/migrations/env.py` for Alembic |
| Re-sync the recipe catalog after editing seed data | `backend/app/seed.py` `seed()` - adds/updates/removes rows to exactly match `backend/app/seed_data.json`, safe to re-run; run `alembic upgrade head` first so the table exists |
| Change image upload/storage (currently Cloudinary) | `backend/app/cloudinary_client.py` (SDK config), `backend/app/routers/images.py` `upload_image()` - swap the `cloudinary.uploader.upload()` call for a different provider here if needed |
| Let users create/edit/delete/twist recipes, or change visibility/official rules | `backend/app/routers/recipes.py` (`create_recipe()`, `update_recipe()`, `delete_recipe()`, `twist_recipe()`, `set_official()`), `backend/app/schemas.py` `RecipeIn`/`RecipeUpdateIn`/`OfficialUpdateIn` |

## File index

- `backend/app/main.py` - FastAPI app: CORS middleware from `Settings.cors_origin_list`, mounts `auth`, `images`, `recipes`, and `storage` routers. Schema is Alembic-managed, not created on startup.
- `backend/app/config.py` - `Settings` (pydantic-settings): `database_url`, `cors_origins`, `secret_key`, `access_token_expire_minutes`, `redis_url`, `cloudinary_cloud_name`, `cloudinary_api_key`, `cloudinary_api_secret`, reads a local .env file (see `backend/.env.example`).
- `backend/app/cache.py` - Redis recipe cache: `cache_get()`/`cache_set()` (JSON, 300s `TTL_SECONDS`, key prefix `PREFIX`) fail open to a miss if Redis is down; `cache_get_bytes()`/`cache_set_bytes()` hold proxied image bytes; `invalidate_recipes()` wipes every `recipes:*` key. `backend/app/routers/recipes.py` caches `list_recipes` (one unfiltered `roots` entry, visibility filtered per caller) and `get_recipe` (`id:<id>`), and calls `invalidate_recipes()` after every commit; `backend/app/seed.py` does too.
- `backend/app/database.py` - SQLAlchemy `engine`, `SessionLocal`, `Base`, `get_db()` dependency.
- `backend/app/models.py` - `RecipeRow` (`id`, `data` JSON for content fields, plus real columns `owner_id` (nullable FK to `users.id`, null for seed/system recipes), `is_public` (default true), `is_official` (default false, admin-curated), `parent_recipe_id` (nullable self-FK - set when this recipe is a twist of another)), `UserRow` (`username`, `hashed_password`, `name`, `is_admin` - accounts are username/password, no email), `AppStorageRow` (`user_id` + `key` composite PK, `value` JSON) - one row per account per key.
- `backend/app/security.py` - `hash_password()`/`verify_password()` (bcrypt), `create_access_token()` (JWT via pyjwt), `get_current_user()` - a FastAPI dependency that reads the `Authorization: Bearer` header and resolves a `UserRow`, raising 401 if missing/invalid/expired; `get_current_user_optional()` - same but returns `None` instead of raising, used by endpoints that behave differently for a logged-in caller without requiring one; `require_admin()` - wraps `get_current_user`, raises 403 if `not current_user.is_admin`.
- `backend/app/cloudinary_client.py` - configures the `cloudinary` SDK from settings at import time; imported (not called) by `backend/app/routers/images.py` purely for its side effect.
- `backend/app/schemas.py` - `StorageValue` (generic storage body), `RegisterRequest`, `LoginRequest`, `UserOut` (includes `isAdmin`), `TokenResponse`, `IngredientIn`/`RecipeStepIn`/`NutritionInfoIn`/`RecipeIn` (recipe-creation payload, `steps` optional - loosely typed `str` fields for category/difficulty/etc rather than mirroring the frontend's literal unions, see Gotchas), `RecipeUpdateIn` (all fields optional, plus `isPublic` to toggle visibility), `OfficialUpdateIn` (`isOfficial`, admin-only).
- `backend/app/routers/auth.py` - `POST /api/auth/register`, `POST /api/auth/login` (both return a `TokenResponse` with the JWT and user), `GET /api/auth/me` (protected) - all three include `isAdmin` in the returned `UserOut`.
- `backend/app/routers/images.py` - `POST /api/images` (protected) - accepts a multipart `file`, rejects anything over 8MB or outside `ALLOWED_CONTENT_TYPES`, uploads to Cloudinary with `format="avif"` (always transcoded, regardless of the source format - see Gotchas), returns `{"url": secure_url}`. Also `GET /api/images/proxy` (`proxy_image`, public) - dev helper: fetches a `res.cloudinary.com` image URL (anything else is a 400, so it isn't an open proxy) and caches the bytes in Redis for 24h, so a phone on the PC's hotspot never has to reach Cloudinary.
- `backend/app/routers/recipes.py` - `_to_response(row, db)` merges a `RecipeRow`'s `data` blob with its ownership/visibility/curation/lineage columns, plus a live `twistCount` (a count query against `parent_recipe_id` - one extra query per row, fine at this project's scale, not worth denormalizing), into the flat shape the frontend expects; every handler below returns through it. `GET /api/recipes` (`list_recipes`, optional auth) - discovery/browse catalog, root recipes only (`parent_recipe_id IS NULL`), filtered to public plus the caller's own. `GET /api/recipes/mine` (`list_my_recipes`, protected) - all of the caller's own recipes, root or twist, any visibility; declared before `/{recipe_id}` so FastAPI doesn't match "mine" as an id. `GET /api/recipes/{recipe_id}` (`get_recipe`) - no visibility check at all, "unlisted" not deleted once private, used for direct links and anything that already references the id. `GET /api/recipes/{recipe_id}/twists` (`list_twists`, optional auth) - public/own twists of a recipe. `POST /api/recipes` (`create_recipe`, protected) - validates against `RecipeIn`, assigns a server-side `id` (`uuid.uuid4().hex[:12]`, not client-generated - see frontend.md gotcha G6), sets `owner_id`/`is_public=true`/`is_official=false`/`parent_recipe_id=null`, and `rating`/`reviewCount`/`author`/`dateAdded` from server state, ignoring whatever the client sent. `PATCH /api/recipes/{recipe_id}` (`update_recipe`, owner-only) - edits any `RecipeUpdateIn` field and/or toggles `isPublic`. `POST /api/recipes/{recipe_id}/twist` (`twist_recipe`, protected) - forks a copy (new id, `owner_id`=caller, `is_public=false`, `parent_recipe_id`=original), reset rating/reviewCount/author/dateAdded, never blocked from twisting your own recipe server-side (the frontend just doesn't offer the button). `PATCH /api/recipes/{recipe_id}/official` (`set_official`, admin-only via `require_admin`) - curates `is_official`. `DELETE /api/recipes/{recipe_id}` (`delete_recipe`, owner-only, 204 on success) - before deleting, orphans any twists (`parent_recipe_id` set to null) rather than cascading the delete into them, since a twist is a full independent copy of the data, not just a reference - another user's twist should survive the original being deleted.
- `backend/app/routers/storage.py` - `GET/PUT/DELETE /api/storage/{key}` - all three depend on `get_current_user` and scope to `(current_user.id, key)`, so every account-linked read/write (favorites, ratings, meal plan, etc.) requires login even though recipe browsing doesn't.
- `backend/app/seed.py` - `seed()` - loads `backend/app/seed_data.json`, adds new ids (as `owner_id=None, is_public=True, is_official=True, parent_recipe_id=None` - the cookbook recipes are "official" by origin), updates changed ones, deletes any recipe row whose id isn't in the file (full sync, not additive).
- `backend/app/seed_data.json` - JSON dump of `MOCK_RECIPES` from `src/app/data/mock-recipes.ts` (2 Italian dishes; regenerate with a small Node/TS script if the seed data changes, there is no automated sync).
- `backend/migrations/env.py` - Alembic environment: drives `sqlalchemy.url` from `Settings.database_url` and `target_metadata` from `Base.metadata` (via `backend/app/models.py`) instead of `alembic.ini`, so migrations always target the same DB and schema as the running app.
- `backend/migrations/versions/` - one file per migration; `84e71ad0e7c3` is the baseline (matches the schema create_all used to make, for stamping an existing DB), `45a7d7abcb9e` adds the ownership/visibility/curation/lineage/admin columns.

## Gotchas

- No password reset flow (and no email at all - accounts are username/password) - `register`/`login`/`me` are the only auth endpoints. A "forgot password" flow would need some other recovery channel (e.g. a security question or admin reset), since there's no email to send a reset link to.
- `backend/app/seed_data.json` is a point-in-time export, not a build artifact. If `src/app/data/mock-recipes.ts` changes, re-export and re-run `python -m app.seed` by hand.
- `Settings.secret_key` defaults to a dev-only placeholder; any real deployment must set `SECRET_KEY` in `.env` to a long random value, or every issued JWT becomes forgeable.
- Image storage is Cloudinary, credentials come from `backend/.env` (`CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET`). A wrong API secret fails as `cloudinary.exceptions.Error: Invalid Signature` (500) - the API key and secret are two different values on Cloudinary's dashboard (Settings -> API Keys, secret needs "reveal"), don't confuse them.
- `backend/app/routers/recipes.py` `create_recipe()` and `backend/app/schemas.py` `RecipeIn` don't validate `category`/`difficulty`/`dietaryRestrictions`/`cuisineType` against the frontend's literal unions (they're plain `str`/`list[str]`) - a bad value from a non-frontend client would be stored as-is and only misbehave client-side (e.g. failing to match a filter chip). Tighten with `Literal[...]` if that becomes a real problem.
- No admin UI exists yet - promoting a user to admin (to curate the "official" badge) is a hand-run `UPDATE users SET is_admin = 1 WHERE username = '...'`.
- In `backend/app/routers/recipes.py`, route order matters: `/mine` is declared before `/{recipe_id}` so FastAPI's path matching doesn't treat "mine" as a `recipe_id`. Keep any new fixed-segment route ahead of the `{recipe_id}` catch-all.
